

## 📘 모범답안 정리

### 1. Bento와 Yatai의 역할
- **Bento**는 ML 모델을 API로 호출할 수 있게 감싼 **소스코드 집합(tar 파일)**이에요.
  - 모델, 서비스 코드, 의존성(`bentofile.yaml`)이 함께 들어 있어요.
  - **컨테이너 이미지가 아닙니다.**
- **Yatai**는 Bento를 K8s에 배포하고 관리하는 스택이에요. 컴포넌트가 셋입니다.
  - **Yatai (Registry):** 모델과 Bento를 Object Storage에 저장하고 관리하는 대시보드
  - **Yatai Image Builder:** Bento를 컨테이너 이미지로 빌드
  - **Yatai Deployment:** 이미지를 K8s 서비스로 배포 (Swagger와 Ingress도 함께 생성)
- 전체 흐름: **MLflow**(실험 기록, 승인 버전 관리) → **Bento**(승인 버전을 코드와 함께 고정한 배포 단위) → **Yatai**(이미지로 만들어 배포)

### 2. 벤토 빌드 4단계
1. **모델 등록:** `bentoml.mlflow.import_model("random-forest-classifier", model_uri="models:/<이름>/Production")`로 MLflow 모델을 로컬 BentoML 스토어로 가져와요.
2. **서비스 정의:** `service.py`에 API 엔드포인트(`/predict`)를 정의해요. 추론은 Runner 객체가 맡고, Runner는 수평 확장이 가능해요.
3. **`bentofile.yaml` 작성:** 요구사항과 환경 변수를 정의해요.
4. **빌드 후 푸시:** `bentoml build -f bento/bentofile.yaml`로 빌드하고, 푸시해서 Yatai로 보내요.

### 3. API 서버 파드와 러너 파드
- **API 서버 파드**는 프론트엔드예요. 사용자나 다른 앱의 요청을 받아요.
- **러너 파드**는 백엔드예요. 모델을 메모리에 올려 두고 **추론**을 수행해요.
- 통신은 **API 서버가 러너를 호출**해서 예측 결과를 받는 방향이에요.
- 나누는 이유는 **독립적인 스케일링**이에요. 실습에서는 API 서버 1개, 러너 2개였어요.

### 4. Yatai 배포 중 K8s 내부 동작
- **CRD 두 가지**
  - **`BentoRequest`**는 이미지 빌드 요청이에요. 상태는 `IMAGE-EXISTS`, `IMAGE-BUILDER-POD-PHASE` 컬럼으로 봐요.
  - **`BentoDeployment`**는 서비스 배포 요청이에요. `AVAILABLE: True`가 되면 배포 완료예요.
- **이미지 빌드는 K8s Job으로 실행돼요** (`yatai-bento-image-builder-...`). 실습 중 빌더 파드가 **OOM**으로 죽어서 메모리 limit을 늘려 해결했어요.
- **직접 만들지 않아도 된 것:** ① Dockerfile, ② K8s 매니페스트, ③ `/metrics` 엔드포인트. `bentofile.yaml` 하나면 BentoML이 나머지를 처리해요.

### 5. 데이터 드리프트의 정의와 유형
- **정의:** 모델 훈련에 쓴 데이터의 통계적 특성이 시간이 지나며 바뀌어서, 모델의 성능과 정확도가 떨어지는 현상이에요.
- **네 가지 유형**
  - **레이블 드리프트:** 정답 기준이 바뀜 (불량 판정 기준이 바뀌는 경우)
  - **사전 확률 이동:** 클래스 비율이 바뀜 (사기 비율이 바뀌는 경우)
  - **공변량 이동:** 입력 피처 분포가 바뀜 (고객 연령대나 지역이 바뀌는 경우)
  - **급격한 드리프트:** 외부 요인 때문에 갑자기 바뀜 (팬데믹, 큰 시장 사건)

### 6. 통계 검정 세 가지

| 검정 | 피처 유형 | 판정 방식 |
|---|---|---|
| **KS 검정** | 수치형 | CDF를 비교. p-value < 0.05면 드리프트 |
| **카이제곱 검정** | 범주형 | 범주별 분포를 비교. p-value < 0.05면 드리프트 |
| **바서슈타인 거리** | 수치형 | 분포 사이 거리를 측정. 임곗값(0.1)보다 크면 드리프트 |

- 기억법: **"검정은 작으면, 거리는 크면 드리프트"**
- Evidently는 데이터에 맞는 검정을 자동으로 골라 줘요.

### 7. 드리프트 보고서의 2단계 판정
- **Share of Drifted Columns**는 6 ÷ 8 = **0.75**예요.
- 0.75는 데이터셋 임곗값 0.5 이상이라서 **"Dataset Drift is detected"**가 나와요.
- 두 임곗값은 판정 대상이 달라요.
  - **0.1은 컬럼 단위:** 컬럼 하나의 바서슈타인 거리가 0.1을 넘으면 그 컬럼이 드리프트예요.
  - **0.5는 데이터셋 단위:** 드리프트 컬럼의 비율이 0.5 이상이면 데이터셋 전체가 드리프트예요.

### 8. 실시간 API 드리프트 탐지
- **요청마다 검정하지 않는 이유:** 샘플 1개는 분포가 아니라서 검정 결과가 정확하지 않아요.
  - 그래서 **마이크로배치(윈도)**로 최근 N개 요청을 모아서 참조 데이터와 비교해요.
  - `MonitoringService`가 새 요청은 넣고 오래된 요청은 빼다가, 윈도가 꽉 차면 보고서를 실행해요.
- **윈도 50에서 0.875가 나온 이유:** 표본이 너무 작아서 통계 검정이 불안정했고, **거짓 경보**가 난 거예요. 데이터가 실제로 변한 게 아니에요.
- **대응 방법**
  - 윈도를 키운다 (200, 500 등). 비용과 반응 속도 사이의 균형을 봐야 해요.
  - 임곗값을 올린다.
  - 몇 번 연속으로 넘을 때만 알림을 보낸다.

### 9. Kubeflow 노트북 설정
- **PodDefault**는 네임스페이스에 등록해 두는 "파드 기본값"이에요.
  - `selector.matchLabels`와 라벨이 맞는 파드에 환경 변수와 볼륨을 자동으로 주입해요.
  - 예시(`add-proxy-vars`)에서는 프록시 설정과 **`MLFLOW_TRACKING_URI`**가 주입됐어요.
- **어피니티**는 파드를 원하는 라벨의 노드로 **끌어당겨요.** 예를 들어 `compute: small` 노드에 기본으로 배치할 수 있어요.
- **톨러레이션**은 **테인트**가 걸린 노드에 들어갈 수 있게 해 주는 출입증이에요. 톨러레이션이 없는 파드는 그 노드에 들어가지 못해요.
- 메뉴 옵션은 `jupyter-web-app-config` ConfigMap(`spawnerFormDefaults`, `affinityConfig`)으로 바꿔요.
- 워크스페이스 볼륨은 **`/home/jovyan`**에 자동으로 마운트되고, 기존 PVC를 데이터 볼륨으로 추가할 수 있어요.

### 10. KFP 컴포넌트 간 데이터 전달
- **별도의 방법이 필요한 이유:** 컴포넌트마다 **별도의 K8s 파드**에서 격리되어 실행되기 때문이에요.
- **작은 값**은 `-> str`이나 `-> int`로 반환하고, 다음 컴포넌트에서 `.output`으로 받아요.
- **큰 데이터**는 **값이 아니라 경로로** 넘겨요.
  - 보내는 쪽은 `Output[Artifact]` 또는 `Output[Dataset]`의 `.path`에 파일을 써요.
  - 받는 쪽은 `Input[...]`의 `.path`에서 읽어요.
  - 실제 파일은 MinIO `mlpipeline` 버킷(`v2/artifacts/...`)에 저장돼요. Metrics는 MLMD에만 저장돼요.
- **`import`는 함수 안쪽에** 써요. KFP가 함수 본문만 떼어 파드에서 실행하기 때문이에요(`ephemeral_component.py`).
- 패키지는 `base_image`나 `packages_to_install`로 준비해요.
