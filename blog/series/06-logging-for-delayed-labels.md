# [MLOps 실습 시리즈] 6. 지연 라벨을 위한 서빙 로그 설계

정답 라벨은 몇 달 뒤에 온다. 그때 "이 예측이 맞았나?"를 확인하려면, 서빙할 때 무엇을 남겨둬야 할까?

## 처음 로그: 원본 입력 + 예측값

처음엔 이것만 남겼다.
```json
{"age": 39, "workclass": "State-gov", ..., "prediction": 0}
```

이 로그 덕분에 살아난 순간이 있었다. 판정 기준 실험(5편)을 하려면 확률이 필요한데 로그엔 0/1뿐이었다. 다행히 **원본 입력이 있어서** 같은 모델로 확률을 다시 계산할 수 있었다. 하지만 모델이 교체된 뒤였다면 불가능했다.

## 바꾼 로그

```json
{
  "customer_id": "C021346",
  "row": {"age": 27, "workclass": "Private", "...": "..."},
  "prediction": 0,
  "probability": 0.07,
  "model_version": "income_drill:v3ajgtg2",
  "threshold": 0.10,
  "request_time": 1794067896.39
}
```

| 필드 | 이유 |
|---|---|
| `customer_id` | 지연 라벨과 연결하는 키 |
| `row` | 드리프트 감시용 원본 입력 |
| `probability` | 나중에 판정 기준을 바꿔서 다시 평가 |
| `model_version` | 섀도우 배포, A/B 비교, 롤백 |
| `threshold` | 그때 어떤 기준으로 판정했는지 |

## 고민한 것 두 가지

**1. 요청 ID 말고 고객 ID로 통일한 이유**

처음엔 요청 ID가 필요 없다고 생각했다. 그런데 첫 실습의 라벨 연결은 "로그 순서 = 라벨 순서"라는 가정에 기대고 있었다. 서버 워커가 하나고 요청을 순서대로 보냈으니 가능했던 일이다. 워커가 여러 개면 순서가 섞인다.

서버가 만든 요청 ID는 라벨을 보내주는 쪽이 모른다. 그래서 **실무에서 원래 쓰는 고객 ID**로 통일했다.

**2. 원본 입력은 펼치지 말고 묶어서**

```python
{**row, "proba": 0.07}       # 입력에 "proba" 키가 있으면 조용히 덮어써진다
{"row": row, "probability": 0.07}   # 자리가 분리돼서 충돌이 없다
```

## 연결할 때 주의할 점

라벨과 연결해 평가할 때, **재학습에 쓴 고객이 평가 데이터에 섞이면** 신모델이 답을 미리 본 셈이 된다. 이번엔 1,200건 중 284명이 겹쳐서 빼고 평가했다.

## 한 줄 정리

지연 라벨 환경에서 평가는 로그 설계에서 결정된다. 연결할 키가 없으면 평가 자체가 불가능하다.
