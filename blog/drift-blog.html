드리프트 경보가 울렸다. 재학습부터 해야 할까?

UCI Adult 소득 예측 모델에 신규 채널 고객을 서서히 흘려 넣고, BentoML 서빙 → Evidently 드리프트 감시 → 지연 라벨 평가까지 직접 돌려봤다. 결론은 예상과 달랐다. 재학습보다 판정 기준 하나 바꾸는 게 훨씬 컸다.

01요약

무엇을 했나

연소득 50K 초과 여부([0]/[1])를 예측하는 모델을 서빙하던 중, 4번째 윈도우부터 마케팅 신규 채널이 열려 20대 단시간 근로자 비중이 8윈도우에 걸쳐 0%에서 100%로 늘어나는 상황을 만들었다. 라벨은 바로 오지 않고 나중에 도착한다. 이 상황에서 경보를 언제 울리고, 경보가 울리면 무엇을 해야 하는지가 실습의 질문이었다.

한눈에 보는 결과

  • 정상 구간(윈도우 0–3) 오탐 0건, 첫 경보는 윈도우 5 (신규 채널 비중 25%)
  • 드리프트 구간에서 예측 1 비율이 0%까지 떨어졌지만, 라벨을 보니 실제 50K 초과도 1%였다. 정확도 0.99. 모델은 망가지지 않았다.

개념 정리

윈도우
한 번에 묶어서 보는 데이터 구간. 이번엔 요청 200건. 실무에선 1시간, 하루처럼 시간으로 자르는 경우가 많다. 작을수록 우연한 흔들림이 커진다.
PSI
두 분포가 얼마나 다른지. 구간별로 (지금 비율 − 평소 비율) × ln(지금/평소)를 더한다. 0.1 미만 안정, 0.1–0.25 주의, 0.25 이상 큰 변화.
Drift share
드리프트로 판정된 열의 비율. 이번 규칙은 열 단위 PSI > 0.1, 그런 열이 50% 이상이면 데이터셋 경보.
공변량 이동
입력 분포 P(x)는 바뀌고 x → y 관계는 그대로. 신규 채널, 신규 지역, 계절. 모델이 그 영역을 학습 때 충분히 봤다면 계속 잘 맞힌다.
개념 드리프트
같은 입력인데 정답이 달라진다. 물가·최저임금, 사기 수법 변화, 정의 변경. 라벨 없이는 잘 안 보이고, 모델이 진짜로 낡는다.
라벨 이동
정답 비율 P(y) 자체가 바뀐다. 독감 유행기에 같은 증상이어도 독감 환자 비율이 오르는 경우.
지연 라벨
정답이 예측보다 한참 뒤에 도착한다. 소득은 세금 신고 후, 카드 사기는 30–90일 뒤 이의 제기로 확인된다.
AUC vs 판정 기준
AUC는 줄 세우기 능력이라 판정 기준과 무관하다. 순이익은 기준에 따라 크게 달라진다.
비용 기반 기준 p*
p* = CFP / (CFP + CFN). 안내 2,000원, 놓친 가입 150,000원이면 약 1.3%. 확률이 정확하다는 전제가 붙는다.
가중치 재학습
도메인 분류기로 "요즘 고객과 닮은" 옛 샘플에 큰 가중치를 주고 sample_weight로 재학습. 새 라벨이 필요 없다.
섀도우 배포 vs A/B
섀도우는 같은 요청을 받아 예측만 남기고 결과는 쓰지 않는다. A/B는 실제로 결정을 적용해 비즈니스 효과를 잰다.
피처 중요도
트리 기본 중요도(빠르지만 값이 다양한 숫자 열을 과대평가), permutation, SHAP, 열 제거 후 재학습, 상관·상호정보량.

p = min(1.0, max(0.0, (t - 3) / 8))   # 윈도우 0~3: 정상, 이후 8윈도우에 걸쳐 0 → 1

03해결 과정

막힐 때마다 가설을 먼저 적고 확인하는 방식으로 진행했다. 각 단계 옆의 표시는 내 첫 가설의 판정이다.

데이터 다운로드가 멈췄다 가설 O

fetch_openml("adult")이 60초 동안 응답이 없었다. 호스트별로 응답을 비교해 보니 범위가 바로 좁혀졌다.

api.openml.org → 000, 8.0s 타임아웃
pypi.org       → 200, 0.04s

가설은 "openml 서버 문제, UCI에서 직접 받기". UCI 원본 zip은 2.2초 만에 받았다. 그런데 unzip이 없어서 파이썬 zipfile로 풀었다. UCI 원본은 헤더가 없고, 값 앞에 공백이 있고, 결측이 ?이고, test 파일 첫 줄은 주석에 라벨 끝에는 .이 붙어 있어서 로더에서 모두 처리했다.

Q1. 한 건만 들어오면 열이 14개뿐이다 가설 없음 X

학습 때는 5,000건을 한꺼번에 one-hot 해서 102열이 나왔다. 요청은 한 건씩 들어오니 같은 방식으로 one-hot 하면 그 사람 값에 해당하는 14열만 생긴다. 자동완성이 제안한 코드는 그럴듯했지만 두 군데서 터졌다.

one_hot(row)                 → NameError: 정의된 적 없는 함수
get_dummies(...)[COLUMN_LIST] → KeyError: 없는 열 88개
get_dummies(...).reindex(columns=COLUMN_LIST, fill_value=0) → (1, 102)

reindex의 columns는 결과가 가질 열 목록과 순서다. 목록에 없는 열은 버리고, 없던 열은 만든다. fill_value=0은 새로 만든 열을 0으로 채운다. 기본값 NaN이 아니라 0인 이유는 one-hot에서 "해당 없음"이 0이기 때문이다. 이 자리에 reshape(1, -1)도 제안됐는데, 1차원 배열을 1행 2차원으로 바꾸는 코드라 1행 DataFrame에는 필요 없다.

Q2. NaN은 JSON이 될 수 없다 가설 △

스트림을 보내자마자 InvalidJSONError: Out of range float values are not JSON compliant가 났다. 내 가설은 "? 특수문자가 인코딩이 안 된다, -999로 바꾸자"였다. 방향은 맞았지만 원인은 조금 달랐다. na_values="?" 때문에 ?는 읽는 순간 NaN이라는 실수 값이 되고, JSON 표준에는 NaN이 없다. JSON에는 null이 있다. -999 같은 값은 모델과 PSI가 진짜 숫자로 받아들여 "-999살 고객"이 생기므로 쓰면 안 된다.

json=row.astype(object).where(row.notna(), None).to_dict()   # NaN → null

Q3. Evidently로 윈도우별 판정

설치된 Evidently는 0.5.0이라 예전 API를 그대로 썼다. 새 API(from evidently import Report)는 경로와 인자 순서가 다르니 버전부터 확인해야 한다.

from evidently.report import Report
from evidently.metric_preset import DataDriftPreset

r = Report(metrics=[DataDriftPreset(stattest="psi", stattest_threshold=0.1, drift_share=0.5)])
r.run(reference_data=ref, current_data=cur)   # 원본 14열만

결과는 정상 구간 오탐 0건, 첫 경보 윈도우 5였다. 그런데 두 가지가 눈에 띄었다. native-country는 정상 구간에서도 매번 드리프트로 잡혔다. 그리고 필터는 두 열뿐이었는데 최대 12개 열이 같이 잡혔다.

왜 다른 열도 같이 잡혔나. Evidently는 필터를 모른다. 매 윈도우 14개 열 전부를 레퍼런스와 비교할 뿐이다. 20대 단시간 근로자는 결혼 여부, 가족 관계, 학력, 직업도 평소 고객과 다르다. 서로 얽힌 열이 같이 움직인 것이다.

왜 102열이 아니라 14열을 보나. workclass 하나가 one-hot 하면 8개 열로 쪼개진다. 102열로 세면 대부분이 거의 0인 드문 열이고, 200건 윈도우에서는 드문 값 몇 건에도 PSI가 크게 튄다. native-country(41개 국가)가 정확히 그 모습이었다. 경보가 과하게 울리고, "workclass_Never-worked가 바뀌었다" 같은 경보는 해석도 어렵다.

예측 1 비율 0%, 모델이 망가졌나 가설 X

드리프트 구간 끝에서 모델은 200명 전원을 "50K 이하"로 예측했다. 0%는 상식적으로 이상해 보였고, 내 가설은 "모델이 망가졌다, 라벨이 오면 바로 재학습"이었다. 라벨을 확인해 보니 틀렸다.

데이터 드리프트가 곧 성능 저하는 아니다. 입력은 크게 바뀌었지만(age PSI 5.49) "이런 사람은 소득이 이렇다"는 관계는 그대로였다. 공변량 이동이다. 이상하다는 것과 틀렸다는 것은 다르다. 판단 전에 소량이라도 라벨을 확인해야 한다.

중요 피처 기준 규칙

랜덤포레스트 중요도를 원본 열 단위로 합산하니 상위가 age 0.14, fnlwgt 0.13, marital-status 0.10이었다. "상위 3개 중 2개 이상 드리프트면 경보" 규칙은 정상 구간 오탐 0건, 윈도우 5 경보였다. 시점은 14열 규칙과 같지만 잡음이 아니라 실제로 중요한 열 때문에 울렸다.

다만 fnlwgt는 인구조사의 표본 가중치라 소득과 거의 관계가 없다. 트리 기본 중요도가 값이 다양한 숫자 열을 과대평가해서 생긴 결과다. 자동으로 뽑은 중요도도 사람이 검토해야 한다. 이 열은 원래 피처가 아니라 sample_weight로 써야 하는 값이다.

판정 기준만 바꿔보기

상황을 하나 가정했다. 이 모델로 50K 초과 고객에게 프리미엄 카드 안내를 보낸다. 안내 1건에 2,000원, 50K 초과 고객이 가입하면 150,000원이 남는다. 라벨은 3개월 뒤에 오고, 200건 수동 라벨링은 50만 원에 3일이다. 선택지는 즉시 재학습, 3개월 대기, 소량 라벨링, 판정 기준 조정이었고 나는 기준 조정 → 소량 라벨링 순서를 골랐다.

서빙 로그에 확률이 없었지만 원본 14열을 남겨둔 덕에 같은 모델로 확률을 다시 계산할 수 있었다.

새 라벨 없이 가중치 재학습 효과 없음

최근 서빙 입력(라벨 없음)과 레퍼런스를 구분하는 도메인 분류기를 학습하고, 레퍼런스 샘플마다 가중치를 줬다.

w = p(최근|x) / p(옛날|x) × (n_ref / n_new)
model.fit(X_ref, y_ref, sample_weight=w)

# 가중치 20   ← 17세, 주 12시간, 미혼    (요즘 고객과 닮음)
# 가중치 0.05 ← 61세, 주 40시간, 기혼    (요즘 거의 안 들어옴)

AUC는 0.947 → 0.941로 오히려 조금 내려갔다. 랜덤포레스트는 이미 그 영역을 잘 배워뒀고, 가중치를 세게 주면서 유효 샘플 수가 5,000에서 536으로 줄어 불안정해졌다. 이 기법은 단순한 모델이거나 학습 데이터 자체가 편향된 경우(승인된 사람의 상환 기록만 있는 대출 모델 등)에 더 의미가 있다. 실무에서는 재학습보다 "옛 라벨로 새 분포 성능 추정"에 더 자주 쓴다.

로그 다시 설계하기

모델이 교체되면 옛 모델로 확률을 다시 계산할 수 없다. 그래서 서빙 로그를 다시 설계했다.

record = {
    "customer_id": customer_id,       # 실무 고객 ID로 통일, 피처에서 분리
    "row": row,                       # 원본 14열 (묶어서 저장 → 키 충돌 없음)
    "prediction": pred,
    "probability": proba,
    "model_version": MODEL_TAG,
    "threshold": THRESHOLD,
    "request_id": uuid.uuid4().hex,
    "request_time": time.time(),
}

원본을 {**row, "proba": ...}처럼 펼쳐 넣으면, 입력에 같은 이름의 키가 있을 때 나중 값이 앞 값을 에러 없이 덮어쓴다. 처음엔 요청 ID가 필요 없다고 생각했는데, 첫 스트림의 라벨 연결이 "로그 순서 = 라벨 순서"라는 가정(워커 1개, 순차 요청)에 기대고 있었다. 워커가 여러 개면 순서가 섞이고, 서버에서 만든 ID는 라벨을 보내는 쪽이 모른다. 그래서 실무에서 쓰는 고객 ID로 통일했다. BentoML에서 확률을 받으려면 저장할 때 signatures에 predict_proba를 등록해야 한다.

Q5. 고객 ID로 지연 라벨을 연결해 비교

드리프트 구간 1,200건을 고객 ID와 함께 새로 흘렸다. 신모델은 레퍼런스에 첫 스트림의 지연 라벨 3,000건을 더해 재학습했다. 신모델 학습에 쓴 고객이 평가에 섞이면 답을 미리 본 셈이라 뺐다.

05회고

인사이트

  1. 드리프트 경보는 "입력이 바뀌었다"는 신호이지 "모델이 틀린다"는 신호가 아니다. age PSI가 5.49였던 윈도우에서 정확도는 0.99였다. 공변량 이동인지 개념 드리프트인지 구분하는 단계가 경보와 재학습 사이에 있어야 한다.
  2. 가장 싼 개선이 가장 컸다. 재학습, 새 라벨 없이 비용표 하나로 판정 기준을 바꾼 효과가 재학습의 수십 배였다. 기본 기준 50%는 비용 구조를 전혀 반영하지 않은 숫자다.
  3. 감시할 열을 고르는 것도 설계다. 시끄러운 열 하나가 경보 시점을 두 윈도우 당겼다. 다만 항상 그 방향은 아니다. 그 열이 우연히 조용했던 윈도우에선 분모만 줄어 오히려 빨라지고, 해외 채널처럼 그 열이 진짜 첫 신호일 수도 있다.
  4. 원본 입력을 남긴 로그가 실험을 살렸다. 확률을 저장하지 않았는데도 원본 14열 덕에 다시 계산할 수 있었다. 모델이 교체된 뒤라면 불가능했을 일이다.
  5. 자동으로 나온 결과는 사람이 검증해야 한다. 자동완성 코드는 두 군데서 터졌고, 자동 중요도는 의미 없는 fnlwgt를 2위로 올렸다.

같이 논의한 것

최저임금이 오르면? 같은 사람의 명목 소득이 올라 50K 초과가 늘어난다. 개념 드리프트다. 기준을 60K로 올리면 "상위 고소득자"라는 의미는 어느 정도 지킬 수 있지만, 인상은 저소득층에 크게 작용하고 고소득층엔 거의 영향이 없어서 기준만 바꿔서는 부족하다. 카드 자격처럼 명목 금액이 상품이나 법으로 정해져 있으면 기준 자체를 못 바꾼다. 기준 변경은 기술이 아니라 비즈니스 결정이다.

실패 비용은 어떻게 매기나. 기본은 오분류 비용표다. 도메인마다 모양이 다르다.

현실의 벽. 200만 원, 450만 원 차이도 성과로 인정받기까지는 설득이 필요하고, 중소기업은 이 정도 데이터가 쌓이지도 않는 경우가 많다. 컬럼 설계, 수집, 파이프라인, 유지보수 비용이 버는 돈보다 클 수 있다. 그래서 거창한 파이프라인보다 비용표 기반 기준 조정 같은 가벼운 방법이 먼저 가치를 낸다고 생각한다.

실무에서 중요하게 다뤄야 할 것

  • 경보 이후의 순서를 정해두기: 소량 라벨로 성능 확인 → 판정 기준 조정 → 개념 드리프트가 확인되면 재학습. 재학습은 섀도우나 챔피언/챌린저로 검증한 뒤 교체.
  • 열마다 역할 나누기: 파이프라인 고장 감시(결측률·단위 변화, 하나라도 바뀌면 경보), 성능 감시(중요 피처 기준), 참고용(대시보드만).
  • 로그 스키마: 비즈니스 ID, 원본 입력(묶어서), 확률, 모델 버전, 판정 기준, 시각. 지연 라벨과 조인할 키가 없으면 평가 자체가 불가능하다.
  • 라벨 없이 볼 수 있는 것: 예측 분포 변화, 보정된 확률 기반 성능 추정(CBPE, 단 개념 드리프트는 못 잡음), 소량 수동 라벨링.
  • 평가 데이터 누수 막기: 재학습에 쓴 고객이 평가에 섞이지 않게.
  • 환경 재현성: openml 장애, 빠진 unzip, Evidently API 변경, Yatai 아카이브. 도구와 데이터 출처는 언제든 바뀐다.
